# NAS音乐库整理方案

## 一、项目概述

### 1.1 整理目标
- **元信息修复**：自动匹配正确的歌曲标题、艺术家、专辑、封面、歌词等
- **目录规范化**：按艺术家/专辑层级重新组织文件结构
- **异常处理**：记录无法自动处理的歌曲，便于人工干预

### 1.2 音乐库现状
- 音乐数量：约10,000+首
- 问题：元信息混乱、目录结构不规范

## 二、系统能力分析

### 2.1 支持的音乐格式

| 格式 | 扩展名 | 说明 |
|------|--------|------|
| 无损 | flac, ape, wav, aiff, wv, tta, dsf, dff | 推荐使用 |
| 有损 | mp3, m4a, ogg, opus, wma, mpc, wmv | 支持处理 |

### 2.2 支持的元数据刮削源

| 刮削源 | 代码标识 | 特点 | 推荐场景 |
|--------|----------|------|----------|
| 网易云音乐 | `netease` | 中文歌曲丰富，元数据质量高 | **首选**，中文流行音乐 |
| QQ音乐 | `qmusic` | 曲库大，封面质量好 | 中文流行音乐备选 |
| 咪咕音乐 | `migu` | 移动端数据源 | 补充数据源 |
| 酷狗音乐 | `kugou` | K歌资源丰富 | 流行音乐 |
| 酷我音乐 | `kuwo` | 老歌资源多 | 经典老歌 |
| Acoustid | `acoustid` | 音频指纹识别 | 无文件名信息时使用 |
| SmartTag | `smart_tag` | 智能标签匹配 | 综合匹配 |

### 2.3 支持的元数据字段

```
├── 基本信息
│   ├── title        (歌曲标题)
│   ├── artist       (艺术家)
│   └── album        (专辑名称)
├── 扩展信息
│   ├── albumartist  (专辑艺术家)
│   ├── discnumber   (碟号)
│   ├── tracknumber  (音轨号)
│   ├── genre        (流派)
│   └── year         (发行年份)
├── 附加内容
│   ├── lyrics       (歌词)
│   ├── artwork      (专辑封面)
│   ├── comment      (注释)
│   ├── album_type   (专辑类型)
│   └── language     (语言)
```

### 3.2 第一阶段：预扫描分析

**目的**：了解音乐库现状，制定整理策略

**步骤**：
1. 扫描所有音乐文件，统计：
   - 文件格式分布
   - 目录结构现状
   - 现有元数据完整度
   - 文件命名规范程度

2. 生成诊断报告：
   - 无元数据的文件数量
   - 元数据不完整的文件列表
   - 文件名无法解析的歌曲

**执行命令**：
```bash
# 通过API触发全量扫描
GET /api/task/full_scan_folder/
```

### 3.3 第二阶段：元数据修复

#### 3.3.1 刮削策略

**推荐刮削顺序**：
```
网易云音乐 → QQ音乐 → 咪咕音乐 → 酷狗音乐 → 酷我音乐 → Acoustid
```

**匹配模式**：
- `simple` 模式：仅标题完全匹配即可，速度快，适合文件名规范的库
- `strict` 模式：标题+艺术家+专辑综合评分，准确度高，适合混乱的库

#### 3.3.2 分批处理方案

考虑到10,000+首歌曲，建议分批处理：

| 批次 | 数量 | 说明 |
|------|------|------|
| 第1批 | 1,000首 | 测试批次，验证流程 |
| 第2-10批 | 每批1,000首 | 正式处理 |
| 最后批 | 剩余歌曲 | 收尾处理 |

#### 3.3.3 执行方式

**方式一：按文件夹批量处理**
```json
POST /api/task/batch_auto_update_id3/
{
    "file_full_path": "/app/media/music",
    "select_data": [
        {"name": "流行音乐", "icon": "icon-folder"},
        {"name": "经典老歌", "icon": "icon-folder"}
    ],
    "music_info": {
        "select_mode": "strict",
        "source_list": ["netease", "qmusic", "migu", "kugou", "kuwo"]
    }
}
```

**方式二：手动单曲处理（失败歌曲）**
```json
POST /api/task/fetch_id3_by_title/
{
    "resource": "netease",
    "title": "歌曲名称"
}
```

### 3.4 第三阶段：目录整理

#### 3.4.1 推荐目录结构

```
音乐库根目录/
├── 华语流行/
│   ├── 周杰伦/
│   │   ├── 范特西/
│   │   │   ├── 01. 爱在西元前.flac
│   │   │   ├── 02. 简单爱.flac
│   │   │   └── cover.jpg
│   │   └── 叶惠美/
│   ├── 林俊杰/
│   └── ...
├── 欧美流行/
│   ├── Taylor Swift/
│   └── ...
├── 日韩音乐/
│   └── ...
├── 纯音乐/
│   └── ...
└── 未分类/
    └── 无法识别的歌曲/
```

#### 3.4.2 整理规则

**一级目录**：按音乐类型/语言分类
- 华语流行、欧美流行、日韩音乐、纯音乐、古典音乐等

**二级目录**：按艺术家名称
- 使用规范化的艺术家名称

**三级目录**：按专辑名称
- 包含专辑封面 (cover.jpg)
- 包含歌词文件 (.lrc)

**文件命名**：
```
{tracknumber}. {title}.{ext}
示例：01. 爱在西元前.flac
```

#### 3.4.3 执行整理

```json
POST /api/task/tidy_folder/
{
    "file_full_path": "/app/media/music",
    "root_path": "/app/media/music_sorted",
    "select_data": [...],
    "first_dir": "artist",
    "second_dir": "album"
}
```

### 3.5 第四阶段：结果汇总

| song_name | 歌曲名 |
| artist_name | 艺术家 |
| state | 状态 (success/failed/wait) |

## 四、异常处理机制

### 4.1 无法自动匹配的情况

| 问题类型 | 原因 | 解决方案 |
|----------|------|----------|
| 文件名无意义 | 如"01.mp3"、"未知.mp3" | 使用Acoustid音频指纹识别 |
| 多艺术家混淆 | 合集、翻唱、现场版 | 手动选择正确版本 |
| 小众音乐 | 独立音乐人、古风 | 手动搜索补充 |
| 外语歌曲 | 日韩、欧美小众 | 使用对应区域数据源 |
| 翻唱/混音 | 与原曲混淆 | 手动区分版本 |

## 五、执行计划

### 5.1 时间估算

| 阶段 | 预计时间 | 说明 |
|------|----------|------|
| 预扫描分析 | 30分钟 | 扫描文件结构 |
| 元数据修复 | 20-40小时 | 每首歌约5-15秒 |
| 目录整理 | 2-4小时 | 文件移动重命名 |
| 异常处理 | 视情况 | 人工干预部分 |
| **总计** | **约24-48小时** | 建议分多天执行 |

### 5.2 执行建议

1. **先小批量测试**
   - 选择100-200首歌曲测试完整流程
   - 验证刮削准确率
   - 调整匹配策略

2. **分类型处理**
   - 先处理华语流行（网易云匹配率高）
   - 再处理欧美音乐
   - 最后处理小众/古风/纯音乐

3. **备份策略**
   - 整理前完整备份音乐库
   - 或在副本上操作

4. **网络考虑**
   - 刮削需要稳定网络
   - 建议在网速好的时段执行
   - 可考虑使用代理

## 七、注意事项

### 7.1 数据安全

- ⚠️ **强烈建议先备份**：整理过程会修改文件元数据和移动文件
- 建议在音乐库副本上先测试
- 保留原始文件名映射关系

### 7.2 性能优化

- 分批处理，避免一次性处理过多文件
- 网络不稳定时可减少刮削源数量
- 可考虑本地缓存已匹配结果

### 7.3 质量控制

- 定期检查匹配准确率
- 对自动匹配结果进行抽样验证
- 保留失败记录便于后续处理
